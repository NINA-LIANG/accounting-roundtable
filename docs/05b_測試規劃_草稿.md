# 會計圓桌｜第 5 步　測試規劃（v0.1 草稿）

狀態：2026-11-12 Claude 依憲章 v1.0、02 資料決定、需求書 v0.1 代擬，需求者確認後才算數。每一項測試都寫成「什麼情況、應該看到什麼」，讓不寫程式的人也能判斷有沒有做對。第 7 步開發時，每項功能都先寫出會失敗的測試，再寫功能。

## 一、機器閘門（每次改動自動跑，沒過就不能合併）

## 二、每日監控的測試
| 情況 | 應該看到什麼 |
|---|---|
| 某位員工當天沒有日誌 | 監控頁該員工顯示紅色「漏做」，漏做數加一 |
| 員工寫「今日無工作」並附原因 | 顯示「今日無工作」，不算漏做 |
| 同步時有一部法規抓取失敗 | 資料更新顯示紅色，當天不產出發布包 |
| 抽查條文與官方頁面不一致 | 資料更新顯示紅色，列出是哪一部哪一條 |
| 排程當天沒有執行（例如額度用完） | 隔天的檢查把前一天標為「未執行」 |

## 三、人工驗收（第 8 步由需求者本人做）
1. 用手機和電腦各開一次七個固定頁面與監控頁，文字不被切掉、深色底上看得清楚。
2. 在法規知識庫搜尋「交際費」，找得到所得稅法第 37 條與查核準則第 80 條。
3. 隨機點三篇文章的三個條號連結，都連到全國法規資料庫的對應條文。
4. 照需求書第六節走一次口試展示的三個動作。
5. 需求者自己手算三個案例，和網站顯示的答案一致。

## 四、論文評估用的測試（不是閘門，結果寫進研究紀錄）
固定題庫的引用正確率、有無知識庫對照、與人工撰寫的比較，方法見 ai-content-company/research-log/研究設計草案.md。

## 五、還沒辦法測的事（先寫明，不假裝有測）
1. 白話解讀是否正確：程式只能驗引文，解讀仍要本人核對與專家評分。
2. 解釋函令與準則公報尚未收錄，相關題目只會被標「知識庫未涵蓋」。
3. 社群平台貼文是手動，網站無法驗證貼出去的內容與發布包一致。
