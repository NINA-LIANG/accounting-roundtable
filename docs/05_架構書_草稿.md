# 會計圓桌｜第 5 步　架構書（v0.1 草稿）

狀態：2026-11-12 Claude 依建站模板與已定案文件代擬，需求者確認後才算數。標【請需求者決定】的地方不由 Claude 決定。

## 一、整體做法
靜態網站，放在 GitHub Pages，不用資料庫。所有內容（文章、法規、同步紀錄、勘誤）都是 repository 裡的檔案，改動一律走 Pull Request，通過機器閘門才能合併。這是建站模板的固定做法，也讓口試委員能從檔案歷史看到每一次改動。

## 二、資料夾（柱子地圖）
| 資料夾 | 放什麼 | 對應固定頁面 |
|---|---|---|
| docs/ | 定位、憲章、資料來源、需求書、架構書、測試規劃 | 憲章 |
| data/laws/ | 12 部法規逐條 JSON | 法規知識庫 |
| data/sync/ | 同步紀錄與異動清單 | 資料來源與同步紀錄 |
| content/articles/ | 每篇文章一個檔，含引用清單、核准人、核准時間、修改程度 | 首頁、文章頁 |
| content/errata/ | 勘誤紀錄 | 勘誤 |
| logs/daily/ | 每天一個檔，七位員工各一筆工作日誌，加上當日檢查結果與資料更新驗證結果 | 工作日誌與監控 |
| site/ | 版面與樣式（風格 C） | 全部 |
| scripts/ | 同步法規、引用比對、關卡檢查、產生網站 | — |
| tests/ | 三個手算案例與各閘門的測試 | — |
| .github/workflows/ | 機器閘門與每週同步排程 | — |

## 三、一篇文章怎麼從題目走到上線
1. 每週排程同步法規，產生異動清單。
2. AI 員工依序產出題目、文章、腳本、圖卡文字稿、發布包，存成一個草稿 Pull Request。
3. 機器閘門自動檢查：引用比對、知識庫是否 7 天內同步過、警語、禁語、「最新」是否附同步日期。
4. 本人在 Pull Request 上按核准並合併，這就是憲章說的「每篇發布前由本人核准」。
5. 合併後網站自動更新；社群平台由本人拿發布包手動貼文。

## 三之一、每日監控（2026-11-12 需求者新增）
每天固定時間由排程執行一次檢查：讀當天的工作日誌，對照每位員工該做的事，缺的標為漏做；同時檢查知識庫最後同步時間與抽查比對結果。檢查結果寫回 logs/daily/ 並更新監控頁。這項檢查是程式規則，不由 AI 判斷，也不需要 API 金鑰。

## 四、AI 員工在哪裡執行【請需求者決定】
| 選項 | 做法 | 代價 |
|---|---|---|
| 甲 | 在 GitHub Actions 排程自動跑，需要一把 Anthropic API 金鑰存成 repository 的 secret | 要申請金鑰並依用量付費；最接近「自主產出」 |

決定（2026-11-12 需求者原話：「其實打算用甲方式，但還沒花錢」）：目標採甲。金鑰還沒申請之前的過渡做法：排程照樣每天跑，但只做不需要金鑰的事（法規同步、資料驗證、每日監控、機器閘門）；AI 產出的部分先沿用現有原型製作台（丙）。日後把金鑰放進 repository 設定，排程就自動開始產出草稿，不需要改架構。

更新（2026-11-12 需求者同意）：先不用付費金鑰，改用 Claude 排程任務「會計圓桌每日工作」，每天台北時間 07:51 執行，使用現有方案額度；照 06_每日工作手冊.md 做資料同步與驗證、七位員工工作、工作日誌、監控總表。之後額度不夠再換付費金鑰。法規同步因此實際上是每天一次。
